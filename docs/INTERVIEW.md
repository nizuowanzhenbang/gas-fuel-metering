# 面试演示：可复核的燃气计量对账

## 问题与实现

原来的 `max(counter) - min(counter)` 会掩盖计数器复位，也可能把一条读数解释成零用量，或把缺少一个站点的汇总量与完整上游日报比较。本次将数据质量作为对账的前置条件。

| 检查 | 行为 |
| --- | --- |
| 每站至少两条 VALID 读数 | 不满足则中止整个气源的对账，不把缺失站点当成零用量 |
| 日对账有当日、次日 00:00 UTC 边界 | 未覆盖完整业务日则返回 INCOMPLETE_DAY，不按比例外推 |
| 累计量按时间单调不减 | 回退返回 COUNTER_ROLLBACK，等待核实换表或复位，不猜测修正值 |
| 同回路同时间多条有效读数 | 返回 DUPLICATE_TIMESTAMP，不任意挑选一条 |
| 主备首末时间一致 | 否则返回 MISALIGNED_LOOPS，避免对比不同采样区间 |
| 数值有限、非负 | 无效数字不能生成正常判定或触发 JSON 序列化错误 |

通过检查后用 `末值 - 首值` 计算。数据库 Numeric 累计量先以 Decimal 相减，最后转换为现有 API 数值类型。接口返回站点、回路、首末时间与累计值、有效/排除读数数、计算体积及问题代码。数据有问题返回 409 和证据，不返回 PASS/WARN/FAIL。

计量规则在 `backend/services/metering_quality.py` 集中实现。手动 API、Excel 日报及两类主备定时扫描调用同一实现。调度器在数据不合格时跳过偏差计算并写结构化含义明确的警告日志；本次没有增加独立的数据质量告警工单。

## 接口兼容性变化

日对账的结束边界从“当天最后一条”收紧为“次日零点”。次日零点读数作为前一天的闭合边界，也可作为次日的起点；相邻日不会重复累计体积。业务日期仍按既有 UTC 定义解释。真实供气合同如约定北京时间、08:00 交接日等口径，应先另行配置业务时区/交接时间，不能直接沿用 UTC 结果。

原有仅 23:59 或缺数的数据将返回 409，这是有意拒绝不完整日报。调用方需补齐合法边界数据后重算，不能用伪造读数绕过检查。全部无读数、缺单回路等数据质量错误也统一为 409；资源不存在仍为 404，无绑定站点为 400。

新的计量写入将带时区时间先转 UTC 再保存，无时区时间按既有约定视为 UTC。SQLite 历史数据如果曾直接写入其他时区，原偏移可能已经丢失；本次不会猜测或批量平移旧时间，需结合原始采集记录核对后重新导入。手动主备比较允许相同的局部观测区间，昨日定时日报则要求完整日边界，两者用途不同。

## 五分钟演示

1. 依 README 在独立演示环境初始化模拟数据；新版种子从昨日 UTC 零点开始，包含完整昨日边界。
2. 用管理员打开“手动日对账”，选择昨日和 `SRC-001`，上游量填 `720000` Nm³。种子模拟的是每小时 30000 Nm³。结果下方展示逐站依据；FAULT 读数计入排除数量。
3. 使用隔离测试展示半天数据、缺站、复位、错位回路，均不生成结论：

```sh
python -m pytest backend/tests/test_reconciliation_quality.py -v
python -m pytest backend/tests/test_scheduler_jobs.py -v
```

4. 导入同一异常日期的 Excel，展示单行错误且后续行仍可处理，说明共享业务规则的意义。
5. 解释为何原来的最大最小值在 `1000 → 10 → 1100` 时失真，而新实现要求人工核对复位事件。

## 面试追问

**数据质量通过是否代表计量准确？** 不代表。它证明被观察到的有效读数通过这些结构性检查，不能发现采样空隙里未记录的复位，也不能证明仪表已校准。排除的数据和采样区间必须一起展示。

**为什么严格要求时间对齐？** 对比不同区间会把时间差误报为计量差。当前采用明确拒绝，不做缺乏校准依据的插值。

**为什么不引入流处理平台？** 当前问题在计量语义和一致的计算规则，集中服务和可复现测试足以覆盖本次范围。接入真实分钟级数据后，再依据规模评估分区、流处理和迟到数据重算。

**有没有完成月结算？** 本次是日对账与主备回路质量检查，没有实现月结算审批或持久化结算凭证。不要把返回的判定描述为已经锁定付款单。
